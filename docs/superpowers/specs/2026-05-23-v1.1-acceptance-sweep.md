### F2. On a recurrence's scheduled date at 8:00am local, a notification fires with the correct copy and merge fields.

❌ **GAP — CRITICAL** — no production code path schedules a `.recurrence` notification via `Scheduler.schedule(payload: .recurrence(...))`.

Search results (`grep -rEn "SchedulerPayload\.recurrence|payload: \.recurrence"` in `App/Sources/` and `Packages/BillableCore/Sources/`): the `.recurrence` enum case is referenced only in `SchedulerPayload.swift` encode/decode helpers and in test code (`SchedulingTests.swift:108`). `InvoiceGeneratorView.saveRecurrence()` creates the `RecurrenceTemplate` with a `nextFireDate` but never calls `Scheduler.schedule(...)`. Same for `RecurrenceEditorView.save()`.

The Scheduler infrastructure is fully built and tested; the Phase 3 wiring step that calls it on template insert (and on save when `nextFireDate` changes) is missing. Result: at 8am on the scheduled date, no notification will fire. The Catch-up banner on Today still surfaces pending materializations when the user opens the app, but the spec promises an iOS notification.

There is also no notification-copy generator equivalent of `ReminderService.notificationTitle/notificationBody` for the recurrence side — the Phase 1 placeholder copy in `Scheduler.resyncOnLaunch` (title "Cadence", body "Tap to review.") would be the only fallback if scheduling were wired.

### F10. Deleting a client cascades to delete its RecurrenceTemplate rows and cancel their Scheduler entries.

❌ **GAP**
- `Client.swift:23` declares only `@Relationship(deleteRule: .cascade, inverse: \Project.client)`. No cascade to `RecurrenceTemplate`.
- `RecurrenceTemplate.swift:10` carries a comment that the cascade is "explicitly in `ClientEditorView`" — but `grep -rn "RecurrenceTemplate" App/Sources/Features/Clients/` returns no hits. Deletion in `ClientsView.swift:70` is a plain `modelContext.delete(client)`.

## Robustness (4 criteria)

### R1. After force-quit + relaunch, Scheduler.resyncOnLaunch() restores all pending iOS notifications.

✅ **AUTO**
- `SchedulingTests.swift:199` `Scheduler.resyncOnLaunch re-registers SwiftData rows missing iOS-side` — seeds two `ScheduledNotification` rows, asserts `resyncOnLaunch().reregistered == 2`.
- `SchedulingTests.swift:229` `Scheduler.resyncOnLaunch prunes already-fired (past) rows`.

Production wiring: `RootView.onChange(of: scenePhase)` calls `scheduler.resyncOnLaunch()` on every `.active` transition (`App/Sources/App/RootView.swift:82-92`), which subsumes cold-launch.

### R2. After reinstall, schedules are restored from CloudKit Mirror and re-registered with iOS.

❌ **GAP — UNTESTED**
- The SwiftData container is set up with CloudKit when entitlements are available (`BillableApp.swift:32` — `BillableModelContainer.appGroup(..., cloudKitContainerID:)`).
- `Scheduler.resyncOnLaunch` reads `ScheduledNotification` rows from the local store and re-registers any that iOS doesn't have pending. If CloudKit Mirror has restored those rows on a fresh install, the re-register would naturally pick them up.

But: this only works end-to-end if (a) the CloudKit sync has completed by the time `resyncOnLaunch` runs (no guarantee), and (b) `RecurrenceTemplate` / `InvoiceReminderSchedule` are also mirrored. There is no test covering the reinstall-then-CloudKit-restore scenario, and the device is not currently configured for CloudKit testing in CI.

Requires manual device testing with two devices on the same iCloud account, or post-restore on the same device.

### R3. DST transition does not skip or duplicate a recurring fire across the transition.

❌ **GAP — UNTESTED**
- `grep -in "DST\|daylight"` against the test file returns no hits.
- The cadence-math tests do use `TimeZone(identifier: "America/Los_Angeles")` (which observes DST), but no test case constructs a fire date specifically across a DST boundary (e.g., a weekly Mon fire that brackets the spring-forward day).

The implementation uses `Calendar.dateComponents([.year, .month, .day, .hour, .minute], from: fireAt)` to build a `UNCalendarNotificationTrigger`, which delegates DST handling to `Calendar`. In principle this is correct; in practice the spec calls this out specifically and we have not pinned it with an assertion.

### R4. Two-device simultaneous materialize results in exactly one Invoice persisted and lastFiredAt advancing once.

❌ **GAP — UNTESTED**
- `grep -in "Concurrent\|two.{0,5}[Dd]evice\|simultaneous"` against the test file returns no hits.
- Spec §8 explicitly lists this under "Concurrent materialize" as a desired test case.
- `RecurrenceService.materializeDraft` does no lockout or compare-and-swap on `lastFiredAt`. Two concurrent calls would both pass the `isEnded(now:)` check and both insert an Invoice.

Single-device users won't hit this. With CloudKit sync enabled across two devices, it is a real race. Mitigations via SwiftData `@Attribute(.unique)` on Invoice number generation might dedupe by accident, but this is not explicitly designed for.

### Critical open items (block TestFlight)

1. **F2: No production code path schedules a `.recurrence` notification.** This is the central feature of v1.1's recurring-invoice half. The Scheduler is complete, payloads round-trip, tests pass — but no caller invokes `scheduler.schedule(payload: .recurrence(templateID:), fireAt: template.nextFireDate, ...)` when a `RecurrenceTemplate` is inserted or its `nextFireDate` changes. End result: the catch-up banner works when the user opens the app, but the user gets no proactive notification at 8am on the scheduled day, defeating the headline value of the feature.
2. **F10: Client deletion does not cascade to RecurrenceTemplate, and does not cancel scheduled notifications.** Comments in `RecurrenceTemplate.swift` reference an explicit cascade in `ClientEditorView` that does not exist in code. Result: orphan `RecurrenceTemplate` rows after client delete; orphan iOS pending notification (if F2 were wired). Low-frequency bug but data integrity issue.

### Significant gaps (should be addressed but might ship with risk)

3. **F3 degraded routing**: recurrence-notification tap goes to `.recurringList` (Invoices tab) instead of `InvoicePreviewView` with the generated draft. Documented in code as a deliberate trade-off; spec is stricter.
4. **P3 missing banner on recurring screens** (`RecurringRulesView` has no permission banner; comment in `RecurrenceEditorView` even calls out the gap).
5. **R2 (CloudKit reinstall), R3 (DST), R4 (concurrent materialize)** are all completely untested. R3 is most likely a non-bug given `Calendar`'s correctness; R4 is most likely a real bug but rare.
