## Purpose

Lock the rollout order for the 8 enhancement items worth doing from the
post-v1.3 backlog (A1, A2, A3, A4, A5, A6, A7, A8, A10 — A9 is already
shipped). This document is the meta-plan; each phase below will produce its
own design doc when it's its turn to ship.

## Scope of this document

This is **not** the implementation plan for any single phase. It is the
sequencing decision: which items group together, in what order, and why.

The actual code-level designs and implementation plans for each phase will be
authored separately when the phase is picked up.

## The four releases

### Hygiene (standalone PR — no phase, lands whenever) — A10

**Items:** A10 — `@Query` / `FetchDescriptor` bounds sweep
**Value:** Low (invisible to users)
**Effort:** XS (1-2 hours)
**Story:** Pre-flight cleanup mirroring the 2026-05-27 perf fix on
`TodayView.stoppedEntries` (commit `f9fff44`).

**Why standalone:**

- Self-contained: grep, inspect each consumer, add `fetchLimit` where it
  reads only `.first` / `.count`, commit
- No dependencies on or from any other backlog item
- Zero user-visible change → no TestFlight value
- Putting it in a phase artificially gates a 1-2 hour task

**When to ship:** ideally as a "warm-up" PR before Phase 1 begins, or in
parallel with Phase 1 on a separate branch. Don't tie to a release.

### Phase 1 — Invoice professionalism — A1 + A2 + A8

**Items:**

- A1 — Logo upload on Business Profile, rendered in PDF header
- A2 — Tax ID / VAT number on Business Profile + PDF
- A8 — Inline edit of draft line-item descriptions

**Value:** High × 3 (~85% of the total backlog-A value lift per the
2026-05-27 monetization assessment)
**Effort:** ~3-4 days
**Story:** "Cadence invoices now look as professional as your work." Every
invoice the user has ever sent or will send improves. Compliance unlock for
KSA, EU, UK, AU, IN users (A2). Hand-edited descriptions turn auto-summary
into "my work" (A8). Branded header (A1) closes the "made in a free tool"
perception gap.

**Why these three together:**

1. **Migration locality.** A1 and A2 both add fields to `BusinessProfile`
   and immutable snapshots to `Invoice`. Doing them in one phase is one
   schema migration, one round of PDF rendering tests, one TestFlight build.
   Splitting would cost two migrations and two render-test sweeps.

2. **Narrative tightness.** "Invoice professionalism release" is the
   cleanest possible TestFlight story — every change shows up on the
   customer's customer's screen, every change reinforces Pro's value.

3. **A8's narrative inclusion overrides its code-locality argument.** A8
   touches `InvoiceDetailView` (separate from A1/A2's
   `BusinessProfileEditorView` + `InvoiceTemplate` touches), so a strict
   code-locality view would put A8 in Phase 2. But the user-perceived value
   of "auto-summary → my work" is large enough that splitting it from logo
   + VAT would feel like a missed release. Narrative wins.

**Confidence on this phase: 95%.**

**Code surfaces touched:**

- `Packages/BillableCore/Sources/BillableCore/Models/BusinessProfile.swift`
- `Packages/BillableCore/Sources/BillableCore/Models/Invoice.swift`
- `Packages/BillableCore/Sources/BillableCore/Invoicing/InvoiceTemplate.swift`
- `Packages/BillableCore/Sources/BillableCore/Invoicing/InvoiceBuilder.swift`
- `App/Sources/Features/Settings/BusinessProfileEditorView.swift`
- `App/Sources/Features/Invoicing/InvoiceDetailView.swift` (A8 only)
- `App/Sources/Features/Invoicing/InvoicePreviewView.swift`
- `Packages/BillableCore/Sources/BillableCore/Persistence/MarketingData.swift`
- Tests across `BillableCoreTests/InvoicePDFRendererTests`, `InvoiceBuilderTests`,
  and `BusinessProfileTests`

**Follows v1.4:** v1.4 (merge `30f7ce4`, tagged `v1.4`) is already in main
and added the same snapshot pattern for bank details on `BusinessProfile`
+ `Invoice` + `InvoiceTemplate`. Phase 1 follows the identical pattern for
three additional fields (logo, taxIDLabel, taxIDNumber) and one new draft
edit surface (A8). Migration sequence is unambiguous: v1.3 → v1.4 (done)
→ Phase 1.

### Phase 2 — Workflow polish — A3 + A4 + A5 + A7

**Items:**

- A3 — Customizable invoice email subject + body templates
- A4 — Inline note field on running timer card
- A5 — Adjust start time on running entry
- A7 — "Days since last invoice" badge on each client row

**Value:** Medium × 4
**Effort:** ~3-4 days
**Story:** "Cadence fits your daily workflow better." Smaller, scattered
changes across Today, Settings, and Clients — collectively a polish release.

**Why these four together:**

- All Medium-value items left after Phase 1
- Each is XS-S sized so the testing surface stays manageable
- Independent of each other — can be sequenced internally in any order
- Independent of Phase 1 (no shared code between A3 and Phase 1, despite both
  touching `BusinessProfile` — A3 is two new String fields, no Invoice
  snapshot needed since email templates use live values not frozen ones)

**Confidence on this phase: 95%.**

**Considered and rejected:** moving A3 to Phase 1 to batch all three
`BusinessProfile` migrations together. Rejected because (a) SwiftData
lightweight additive migrations are cheap individually, and (b) A3's
email-template story would dilute Phase 1's PDF-professionalism narrative.

**Code surfaces touched:**

- A3: `Packages/BillableCore/Sources/BillableCore/Models/BusinessProfile.swift`,

  `Packages/BillableCore/Sources/BillableCore/Reminders/ReminderTemplateRenderer.swift`

## Why this order, not alternatives

Three alternatives considered and rejected:

| Alternative | Why rejected |
|---|---|
| Maximum code locality (7-phase split by file) | Too granular; TestFlight + review overhead per phase eats more time than the migration savings |
| Risk-front-load (A1 + A2 + A3 in Phase 1 to batch all `BusinessProfile` migrations) | Dilutes Phase 1's PDF-professionalism story; SwiftData additive migrations are cheap individually so batching isn't materially safer |
| Move A8 to Phase 2 (pure code locality) | Code-purist correct but loses Phase 1's full High-value impact; narrative tightness wins |
