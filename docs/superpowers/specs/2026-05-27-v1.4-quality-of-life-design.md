# v1.4 Quality-of-Life Design

**Status:** Approved, ready for implementation plan
**Author:** Claude + Louay
**Date:** 27 May 2026
**Parent:** v1.3 (shipped to TestFlight, build 1.3.0 (1))
**Branch target:** `feature/v1.4-quality-of-life` off `main`

## Context

v1.3 is live in TestFlight. Subscriptions verified end-to-end. The user driving the
app on a daily basis surfaced four polish items. One (locale-default currency) was
investigated and dropped because the existing behavior already implements it
correctly — see *Investigated and dropped* below. The remaining three are real
gaps, and a fourth was added during brainstorming (bank details on invoices) that
covers a genuine feature absence for KSA/MENA freelancers who collect payment via
IBAN.

This is not a feature release. It is a polish + one-feature release scoped to the
post-TestFlight feedback loop. No paid-product changes. No new tabs. No model
changes beyond five additive optional fields on `BusinessProfile`.

## Goals

- Reduce visual density and CTA redundancy on the Today screen.
- Make currency one tap from Settings (the surface users actually open).
- Surface developer + contact attribution in About.
- Render bank/wire instructions on PDF invoices so issuers stop having to
  message clients separately about payment routing.

## Non-goals

- Adding tax/regional currency overrides at runtime (locale already drives it).
- Multi-currency per-invoice. Single-currency-per-profile remains the v1 model.
- Multiple bank accounts per issuer. One set of fields per profile.
- Other payment methods (PayPal, Stripe link, Zelle, crypto). Out of scope.
- IBAN/SWIFT format validation. Stored as user-typed strings.
- Re-rendering the App Store paywall screenshot for the new $3.99/$29.99 prices
  (tracked separately in task #154 — not blocking v1.4).

## Investigated and dropped

The codebase already does this. Verified:

- `App/Sources/Features/Onboarding/OnboardingView.swift:121` — hourly rate field
  uses `Locale.current.currencySymbol` for the prefix glyph.
- `Packages/BillableCore/Sources/BillableCore/Models/BusinessProfile.swift:92` —

  `Locale.current.currency?.identifier ?? "USD"`.

Saudi-region devices see SAR. US-region devices see USD. UK-region devices see
GBP. Behavior is correct; the reporter was testing exclusively on a Saudi-region
simulator. No work to do.

beneath the Start timer button. Resume pill (conditional) and the Start timer
button remain.

### Before

```
[Resume Acme · Logo design ▶]    ← Conditional pill (last-stopped <2h ago)
[     ▶  Start timer        ]    ← Big primary button
RECENT
[Acme] [Helio] [Pine]              ← Three quick-pick tiles
```

### After

```
[Resume Acme · Logo design ▶]    ← Conditional pill (unchanged)
[     ▶  Start timer        ]    ← Big primary button (unchanged)
```

### Code changes

File: `App/Sources/Features/Today/TodayView.swift`

1. **Delete** the `QuickStartRow` struct in its entirety (lines 318–376).
2. **Remove** the `QuickStartRow { project in ... }` block from `startActions`
   (lines 137–147). After the change, `startActions` contains only the

window). They now need two taps. Mitigated by the Resume pill covering the
"just stopped" case.

## Section 2 — Currency moves to Settings · Preferences

### Goal

Currency picker is one tap from the Settings root, in a new "Preferences"
section above Business profile. Removed from the Business Profile editor —
single source of truth, single edit surface.

### Before

```
Settings
├── Business profile
│     └── (tap opens editor)
│           ├── Issuer
│           ├── Payment
│           ├── Invoice numbering
│           ├── Tax
│           └── Currency        ← lives here
├── Subscription
├── Reminders
└── About
```

### After

```
Settings
├── Preferences                  ← NEW section, first in the form
│     └── Currency  ─────────→ (CurrencyPickerView, navigationLink picker)
├── Business profile
│     └── (tap opens editor)
│           ├── Issuer
│           ├── Payment
│           ├── Invoice numbering
│           ├── Tax
│           └── Bank details     ← see Section 4 (Currency removed here)
├── Subscription
├── Reminders
└── About
```

### Code changes

1. **Add `Section("Preferences")`** as the first section of the Form in
   `App/Sources/Features/Settings/SettingsView.swift`:

   ```swift
   Section("Preferences") {
       NavigationLink {
           CurrencyPickerView()
       } label: {
           LabeledContent("Currency") {
               Text(profiles.first?.currencyCode
                    ?? Locale.current.currency?.identifier
                    ?? "USD")
                   .foregroundStyle(.secondary)
           }
       }
   }
   ```

2. **Create** `App/Sources/Features/Settings/CurrencyPickerView.swift`:

   ```swift
   import SwiftUI
   import SwiftData
   import BillableCore

   /// Standalone currency picker that reads/writes BusinessProfile.currencyCode.
   /// Creates a profile on first save if none exists (defensive fallback).
   struct CurrencyPickerView: View {
       @Environment(\.modelContext) private var modelContext
       @Query private var profiles: [BusinessProfile]
       @State private var selection: String =
           Locale.current.currency?.identifier ?? "USD"
       @State private var hasLoaded = false

       var body: some View {
           Form {
               Picker("Currency", selection: $selection) {
                   ForEach(CurrencyCatalog.allCodes, id: \.self) { code in
                       Text("\(code) — \(CurrencyCatalog.displayName(for: code))")
                           .tag(code)
                   }
               }
               .pickerStyle(.navigationLink)
           }
           .navigationTitle("Currency")
           .navigationBarTitleDisplayMode(.inline)
           .onAppear { loadIfNeeded() }
           .onChange(of: selection) { _, newValue in save(newValue) }
       }

       private func loadIfNeeded() {
           guard !hasLoaded else { return }
           hasLoaded = true
           if let existing = profiles.first?.currencyCode { selection = existing }
       }

       private func save(_ code: String) {
           let profile = profiles.first ?? {
               let p = BusinessProfile.defaultForCurrentLocale()
               modelContext.insert(p)
               return p
           }()
           profile.currencyCode = code
           profile.updatedAt = .now
           modelContext.saveOrLog("currency picker save")
       }
   }
   ```

3. **Remove from `BusinessProfileEditorView.swift`**:
   - The `Section("Currency")` block (lines 75–82).
   - The `@State private var currencyCode` declaration (line 26).
   - The `currencyCode = profile.currencyCode` line in `loadIfNeeded()` (line 109).
   - The `profile.currencyCode = currencyCode` line in `save()` (line 124).
   - `currencyCode` is no longer used inside this view; the model continues to
     carry the property and Settings owns reads/writes.

4. The Settings → Business profile row's subtitle (line 22) continues to read
   `profile.currencyCode` as a read-only summary. No change.

### Testing

- `CurrencyPickerView` smoke test: selecting a code persists it to the singleton
  profile.
- Ensure Business Profile editor still saves without `currencyCode` state.
- Existing currency-related tests (`CurrencyCatalogTests`) untouched.

### Risk

Migration-free. `BusinessProfile.currencyCode` storage is unchanged. Existing
users will find their previously-set currency at the new location on first
upgrade.

## Section 4 — Bank details on Business Profile + PDF invoice

### Goal

Issuer can enter wire-transfer details once on their Business Profile. Those
details render on every PDF invoice in a "Payment Details" section, only when
at least one bank field is non-empty.

### Fields

Five optional `String` fields, all default `""`:

1. `bankBeneficiaryName` — e.g., "Studio Lina LLC"
2. `bankName` — e.g., "Riyad Bank"
3. `bankLocation` — e.g., "Riyadh, Saudi Arabia"
4. `bankIBAN` — e.g., "SA03 8000 0000 6080 1016 7519"
5. `bankSWIFT` — e.g., "RIBLSARI" (BIC). Optional; for international wires.

### 4a — Data model

File: `Packages/BillableCore/Sources/BillableCore/Models/BusinessProfile.swift`

Add five fields to the `@Model class BusinessProfile`:

```swift
public var bankBeneficiaryName: String = ""
public var bankName: String = ""
public var bankLocation: String = ""
public var bankIBAN: String = ""
public var bankSWIFT: String = ""
```

Add a computed property near the existing computed helpers:

```swift
public var hasBankDetails: Bool {
    !bankBeneficiaryName.isEmpty
        || !bankName.isEmpty
        || !bankIBAN.isEmpty
        || !bankSWIFT.isEmpty
}
```

Update the existing `init` to accept the five fields as optional params with
default `""` (so tests can ignore them and existing call sites compile).

SwiftData treats added properties with default values as a **lightweight
migration**: existing local records and CloudKit records load with `""`
defaults, no manual migration required.

### 4b — Editor section

In `App/Sources/Features/Settings/BusinessProfileEditorView.swift`, add a new
section after the existing "Tax" section (and before the now-removed
"Currency"):

```swift
Section {
    TextField("Beneficiary name", text: $bankBeneficiaryName)
        .textInputAutocapitalization(.words)
    TextField("Bank name", text: $bankName)
        .textInputAutocapitalization(.words)
    TextField("Location (city, country)", text: $bankLocation)
        .textInputAutocapitalization(.words)
    TextField("IBAN", text: $bankIBAN)
        .autocorrectionDisabled()
        .textInputAutocapitalization(.characters)
    TextField("SWIFT / BIC (optional)", text: $bankSWIFT)
        .autocorrectionDisabled()
        .textInputAutocapitalization(.characters)
} header: { Text("Bank details") }
  footer: { Text("Shown on invoices so clients know where to pay. Leave blank to hide.") }
```

Add corresponding `@State private var bank…: String = ""` declarations for all
five fields. In `loadIfNeeded()`, copy each from `profile.bank…`. In `save()`,
write each back to `profile.bank…`.

### 4c — PDF invoice rendering

File: `Packages/BillableCore/Sources/BillableCore/Invoices/InvoicePDFRenderer.swift`
(verify exact path during implementation).

Add a new renderer block that draws **only when `profile.hasBankDetails == true`**,
positioned **after the totals block, before the footer/watermark**:

Visual format (key/value rows, each empty field skipped):

```
─────────────────────────────────────────
PAYMENT DETAILS
Beneficiary:  Studio Lina LLC
Bank:         Riyad Bank
Location:     Riyadh, Saudi Arabia
IBAN:         SA03 8000 0000 6080 1016 7519
SWIFT/BIC:    RIBLSARI                       ← only if non-empty
```

Style requirements:

- Section header: same typography as existing section headers in the renderer
  (likely SF semibold ~12pt, uppercased, tracking applied — match existing
  TOTALS or NOTES headers).
- Key column: regular body weight, ~10–11pt, label color.
- Value column: monospaced for IBAN and SWIFT (so spaces in IBAN align
  cleanly); regular for others.
- Padding: matches existing inter-section spacing (likely 8–12pt vertical
  before the header).

Conditional rendering rules:

- If `hasBankDetails == false` → entire block (header + rows) is omitted; no
  empty space added.
- Each individual field rendered as a row only if its value is non-empty.
- Order of rows is fixed: Beneficiary, Bank, Location, IBAN, SWIFT/BIC.

### 4d — Tests

`BusinessProfileTests`:

- Default `BusinessProfile()` has all five bank fields equal to `""`.
- `hasBankDetails` returns `false` for default profile.
- Setting any one of the four required-trigger fields (Beneficiary, Bank, IBAN,
  SWIFT) flips `hasBankDetails` to `true`.
- Setting only `bankLocation` does **not** flip `hasBankDetails` (location
  alone is not meaningful payment info).

`InvoicePDFRendererTests` (existing or new):

- When `profile.hasBankDetails == false`, the rendered PDF text content does
  not contain "PAYMENT DETAILS".
- When all five fields filled, all five labels and values appear in the PDF
  text content in the specified order.
- When SWIFT is empty but others filled, four rows render and "SWIFT/BIC:"
  does not appear.
- Page break does not split the PAYMENT DETAILS section mid-block (deferred —
  test only if the existing renderer supports page-break assertions).

### Risk

- **Schema migration:** Additive, all optional with defaults. Lightweight
  migration handles this in SwiftData. CloudKit will sync the new fields;
  devices on older app versions silently ignore them (and don't lose them on
  save).
- **PDF layout overflow:** A long IBAN + a Notes section could push content
  off the page on dense invoices. Existing renderer paginates; tests assert
  block ordering, not pixel position.
- **No paywall implication:** Bank details are core invoice content, available
  to free tier (with watermark) just like the rest of the invoice. Not Pro-gated.

## Acceptance criteria

A v1.4 implementation is complete when:

- [ ] TodayView in idle state renders exactly two CTAs: Resume pill (conditional)
      and the Start timer button. No "RECENT" header, no quick-pick tiles.
- [ ] Settings shows a "Preferences" section at the top with a Currency row.
      Tapping it opens a full ISO-4217 picker.
- [ ] Business Profile editor no longer contains a Currency section.
- [ ] Currency selected in Preferences persists across app relaunches and
      reflects on the Business Profile row's subtitle.
- [ ] Settings → About shows three rows: Version, Developer ("Cadence by Elden
      Studios Company"), Contact (tappable email link).
- [ ] BusinessProfile model has five new bank fields, defaulting to empty.
- [ ] Business Profile editor has a "Bank details" section with five fields and
      saves them.
- [ ] Generated PDF invoice for a profile with at least one bank field set
      includes a "PAYMENT DETAILS" section with the populated rows in the
      specified order, no empty rows.
- [ ] Generated PDF invoice for a profile with all bank fields empty has no
      "PAYMENT DETAILS" section.
- [ ] Existing test suite passes. New tests for bank fields + PDF rendering pass.
- [ ] App launches cleanly on a device with existing v1.3 data installed (no
      crash on lightweight migration; bank fields appear as empty in editor).
